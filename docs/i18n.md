# 画面の文言(日本語・英語)の管理

アプリの中に出る文字(ボタン名・メッセージなど)を、どこで管理しているかの説明です。

## 結論

- 文言は、**ソースの中の「辞書」(TypeScript のファイル)**で管理しています。外部の「置換ファイル」(JSON など)は、**いまは要りません**。
- 日本語を基本として、英語を同じ場所に並べて書きます。Windows の表示言語が日本語なら日本語、それ以外は英語で表示します。

## どこにあるか

| 対象                                 | 場所                                                                                       | 書き方                                                                                                                                                                                                                                                    |
| ------------------------------------ | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ランチャー本体の画面(約 190 個)      | `src/launcher/shared/i18n/messages.ja.ts` と `messages.en.ts`(取り出す `t()` は `i18n.ts`) | `ja`(日本語)と `en`(英語)の 2 つのオブジェクト。画面では `t("settings")` のように呼ぶ。`{name}` のような部分は、`t("key", { name: "…" })` で置き換える                                                                                                    |
| ウィジェット・ミニアプリ(React 側)   | それぞれのフォルダの `i18n.ts`(例: `src/widgets/timer/i18n.ts`)                            | `defineMessages(日本語, 英語)`。そのウィジェットの文言だけを持つ(本体の辞書には足さない)                                                                                                                                                                  |
| ミニアプリの画面(HTML / JavaScript)  | そのミニアプリの `controller/` の、最初に読み込むファイルの先頭付近                        | `navigator.language` で日本語かを調べて、文言を切り替える(`JA` と `L(日本語, 英語)`。ミニアプリは別画面で動くので、本体の辞書は使えない)。HTML に書いた固定の文言は、日本語以外のとき、JavaScript で英語に置き換える(例: `luckyrush` の `localizeStatic`) |
| トレイのメニュー・初期フォルダの名前 | `src-tauri/src/`(`window/tray.rs`・`config/model.rs`)                                      | Rust 側で、Windows の表示言語(`platform/locale.rs` の `is_ja()`)を見て選ぶ                                                                                                                                                                                |
| ウィジェット・ミニアプリの名前・説明 | `widget.json` / `miniapp.json`                                                             | `name` / `description`(日本語)と `name_en` / `description_en`(英語)                                                                                                                                                                                       |
| 利用者向けの説明(README など)        | `README_JP.md` / `README_EN.md`                                                            | 日本語が基本。英語は別ファイル                                                                                                                                                                                                                            |

## 抜けは、どう防いでいるか

- 本体の辞書は、`ja` のキーが「使えるキー」の型(`Key`)になります。`t("存在しないキー")` と書くと、`tsc`(`npm run check`)が**エラーにします**。
- `en` が `ja` のキーを全部持っているかも、型で検査されます(足し忘れると、エラー)。
- 日本語と英語の**両方**を直すことは、PR のチェックリストに入れています。

## 文言を足す・直す手順

1. 本体なら `src/launcher/shared/i18n/messages.ja.ts` と `messages.en.ts` の両方に、同じキーを足します(用語は、ファイル先頭の「用語の統一」に合わせます)。
2. 画面では `t("キー")` を使います。文字を直書きしません。
3. `npm run check` を通します。

## 「置換ファイル」(外部の文言ファイル)は必要か

**いまは不要です。** 辞書を TypeScript の中に置く利点が大きいためです。

| 方式                          | 利点                                                                               | 欠点                                                                       |
| ----------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| いまの方式(TypeScript の辞書) | キーの書き間違い・抜けを、ビルド前に検査できる。実行時にファイルを読まないので速い | 文言を直すには、再ビルドが要る。コードを触れない翻訳者は、直せない         |
| 外部のファイル(JSON・PO など) | コードを触らずに、文言を差し替えられる。翻訳者・利用者が直せる                     | 検査が弱くなる(キーの抜けは、実行して初めて分かる)。読み込みの仕組みが要る |

外部ファイルに切り替えるのは、次のどれかが必要になったときです。

- 3 言語以上に増やす(たとえば、翻訳を GitHub 上で募集する)
- 利用者が、自分で文言を差し替えられるようにする
- コードを触れない人に、翻訳を任せる

そのときは、`messages.ja.ts` / `messages.en.ts` の辞書を JSON に書き出して読み込む形にします(`t()` の呼び出し側は、変えずに済みます)。

## 言語を足したいとき

いまは「日本語、それ以外は英語」です。たとえば中国語を足すなら、`messages.zh.ts` を足し、`i18n.ts` に読み込んで、`t()` の言語の判定(`navigator.language`)と、Rust 側の `is_ja()` を、言語を返す形に広げます。先に Issue で相談してください。
